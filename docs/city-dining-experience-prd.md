# 城市餐饮体验记录小程序：方向调研与产品需求草案

> 版本：0.1（方向评审稿）  
> 日期：2026-09-10  
> 说明：本文是产品与合规风险建议，不替代执业律师针对实际主体、类目和运营方式出具的正式法律意见。

## 1. 结论先行

项目可以从“AI 食物卡路里识别”转向“城市餐饮体验记录”，但不建议把产品定义为“餐厅黑榜”或“避雷曝光平台”。推荐定位为：

> 帮用户记录自己在哪座城市、哪家店吃过什么、花了多少、哪里不符合预期，并把有依据的亲历体验分享给其他人。

“避雷”可以是用户获得的结果，但不应成为平台煽动负面评价的口号和唯一内容方向。产品应同时容纳“推荐 / 一般 / 谨慎选择”，并把事实记录、个人感受和严重指控分开处理。

上线并不会必然导致微信下架，但公开发布文字、图片并允许他人浏览，已经从私人记录工具变成 UGC 信息发布或社区服务。此时应按实际功能核对微信后台最新服务类目，通常需要“社交-笔记”或“社交-社区/论坛”一类匹配类目，并配置实名、内容审核、举报、申诉、处置和留痕能力。类目或资质不匹配、UGC 无审核、投诉后不处理，才是更直接的拒审或下架因素。

法律风险主要不是“用户说了差评，平台就一定违法”，而是以下几类：

1. 用户虚构消费经历、捏造事实或用侮辱性语言贬损商家，可能侵犯商家名誉权；若发帖者与商家存在竞争关系或受竞争者组织，可能进一步构成商业诋毁。
2. 平台收到合格侵权通知后未及时采取必要措施，或者已经知道、应当知道侵权仍放任传播，可能对扩大部分或相关损害承担责任。
3. 用户上传店员、顾客正脸、聊天记录、电话、订单姓名等，可能侵犯肖像、隐私或个人信息权益。
4. 把负面帖流量化、榜单化，或以付费删帖、付费压制负面、商家充值改排名等方式盈利，会显著放大监管、诉讼和刑事风险。

因此，建议先做“个人记录 + 受控公开”的 MVP，不做全国黑榜、热搜、评论大战、私信、商家付费删帖和现金奖励。

## 2. 当前项目盘点

现有产品是 uni-app 微信小程序 + Go/Gin 服务端，已有：

- 微信登录、用户资料、隐私协议；
- 拍照 / 文字识别食物，生成卡路里和营养素；
- 饮食历史、日/月汇总；
- “吃什么”转盘和自定义菜品；
- 积分、排行榜、连续打卡、成就、邀请和分享海报；
- 图片上传、意见反馈、通知设置；
- AI 模型与提示词配置。

现有后端没有地点、店铺、公开帖子、评论、点赞、举报、商家申诉、内容审核和操作审计等核心社区模型。现有登录只记录 OpenID；公开发布前需要补齐满足实际合规要求的发布者身份核验方案。现有积分围绕“识别次数、三餐、邀请、分享”设计，不能直接沿用到负面内容激励。

可以复用的部分：账号体系、图片上传、用户协议入口、反馈能力、积分/成就框架、分享海报基础设施、Go 服务端与数据库框架。

建议废弃或降级的部分：卡路里首页、营养汇总、AI 食物分析主流程、三餐连续打卡、识别额度奖励。转盘可改成“附近吃什么 / 从我的收藏中抽一家”，但不进入首版核心链路。

## 3. 产品定位

### 3.1 目标用户

- 经常在本地探索餐厅、小吃摊和夜市的用户；
- 出差、旅行前希望快速了解“有哪些具体注意点”的用户；
- 想保留个人消费记忆，而不愿写长篇点评的用户。

### 3.2 核心价值

- 对记录者：30 秒完成一条可回看的到店记录；
- 对浏览者：看到具体问题、发生时间和适用条件，而不是一句情绪化“难吃”；
- 对平台：沉淀结构化、可更新、有证据等级的本地体验数据。

冷启动阶段采用“工具先行、社区渐进”：即使公开体验为零，用户仍可通过店铺搜索、私人足迹、收藏、从附近或收藏中抽选“吃什么”、旧版饮食工具和分享卡片获得独立价值。公开内容不是产品可用的前置条件，而是在真实供给达到一定密度后逐步增强的能力。

### 3.3 产品原则

- 亲历优先：仅鼓励发布本人实际消费或到店经历。
- 事实与感受分开：“等了 45 分钟”是事实陈述，“我觉得不值”是主观感受。
- 时效明确：所有体验必须有到店日期，旧记录降低展示权重。
- 允许纠正：用户可更新，商家可回应，平台可在争议期间限流或隐藏。
- 不奖励负面：奖励完整、真实、及时纠错和有效举报，不奖励“避雷数量”和冲突流量。
- 位置最小化：只在用户主动选择地点时申请定位；公开店铺地点，不公开用户实时位置和轨迹。
- 来源透明：用户体验、编辑实地记录、体验官记录和商家提供资料必须明确区分，不得用虚构账号或模糊标签伪装内容来源。
- 小范围密度优先：冷启动先做一个城市中的少数商圈，不用低质量内容追求全国店铺和信息量覆盖。

## 4. MVP 范围

### 4.1 底部导航

1. **发现**：城市切换、搜索、最新真实体验、按问题标签筛选。
2. **记录**：中心发布按钮，创建到店体验。
3. **足迹**：地图 / 列表查看自己的记录、收藏和草稿。
4. **我的**：贡献分、审核状态、举报与申诉记录、设置和协议。

### 4.2 首页“发现”

- 当前城市手动选择；定位是可选能力，不同意定位仍可使用城市选择和搜索。
- 搜索店名、小吃名、商圈。
- 零公开内容时仍展示合法来源的店铺基础资料、附近店铺、用户自己的足迹和收藏，不显示伪造的热度、评价或用户动态。
- 首页冷启动阶段的优先级为：店铺搜索 / 附近吃什么 → 快速记录 → 我的足迹 → 本地真实体验。公开内容达到运营阈值后，才逐步提高体验信息流的展示权重。
- 筛选：推荐、一般、谨慎选择；价格、服务、口味、排队、卫生观感、宣传不符、其他。
- 卡片展示：店名、城市/商圈、到店月份、人均区间、结论、问题标签、正文摘要、证据状态、最近更新时间。
- 默认按“近期 + 信息完整度”排序；首版不做纯负面热榜、“最坑榜”或围攻式专题。
- 帖子详情提供“有帮助”“信息过时”“涉嫌不实/侵权”按钮。

发现页必须区分以下内容类型：

- `店铺资料`：来自获得授权的地图 / POI 服务或商家提交，只包含店名、地址、分类、营业时间等基础信息，不代表用户评价；
- `用户体验`：登录用户提交的本人真实到店经历，经审核后展示；
- `编辑实地记录`：运营人员实际到店后自行拍摄和撰写，公开标记来源；
- `体验官记录`：受邀体验官的真实到店经历，按普通公开内容完成身份核验和审核；
- `商家提供`：商家提交的菜单、价格、环境和预约说明，明确标记，不混入消费者结论。

当店铺没有公开体验时，详情页显示“暂无真实体验，记录第一条”，不得用演示数据、AI 内容或其他平台内容填充。

### 4.3 发布体验

必填字段：

- 城市；
- 地点 / 店铺（地图 POI 选择，找不到时可提交新地点待审核）；
- 到店日期；
- 消费对象（餐厅 / 小吃摊 / 夜市档口 / 饮品等）；
- 总体结论：推荐 / 一般 / 谨慎选择；

选填字段：

- 体验标签，可不选择；
- 亲历描述，0～500 字，不设最低字数；

- 人均消费区间、排队时长、菜品；
- 图片；
- 消费凭证。凭证默认仅平台审核可见，发布前自动遮盖姓名、电话、订单号等个人信息；
- 可见范围：仅自己 / 公开。首版暂不做好友圈层。

发布页必须有明确提醒：

- 只写本人亲历，不转述未经核实的信息；
- 描述具体时间、行为和结果，避免辱骂、人身攻击；
- 不公开店员或其他顾客的姓名、电话、正脸和聊天账号；
- “食品中毒、违法经营、诈骗、使用违禁品”等严重指控需要可靠证明，否则改写为个人观察或提交监管投诉，不直接公开。

### 4.4 内容状态

`草稿 → 自动检测 → 待人工复核（高风险）/ 已发布（低风险） → 被举报 → 限流或暂时隐藏 → 维持 / 修改 / 删除 → 申诉结束`

以下内容不得自动直发，进入人工复核：

- 指控违法、欺诈、食物中毒、卫生安全事故；
- 出现具体自然人姓名、联系方式、人脸或聊天截图；
- 含侮辱、歧视、威胁或号召围攻、抵制的表达；
- 新账号短时间密集发布同一商家或同一品牌；
- 商家投诉中、短期举报异常增长、疑似竞争对手操纵；
- AI 或规则判断为高度事实争议的内容。

### 4.5 举报与申诉

用户举报理由：虚假经历、侮辱诽谤、侵犯隐私/肖像、广告引流、同行恶意、内容过时、其他。

商家无需成为普通社区用户即可发起权利投诉，但应提供主体身份、与店铺的关系、具体内容链接、侵权初步证据和联系方式。平台应：

1. 生成工单并固定原内容、版本、发布时间、传播数据和审核记录；
2. 判断是否先行限流、遮挡敏感部分或暂时隐藏；
3. 将通知转送发帖用户，允许其提交消费凭证和不侵权声明；
4. 在规则承诺的期限内反馈结果；
5. 支持恢复、修改、删除和双方补充材料，并完整留痕。

MVP 即使不开放评论，也必须有举报、投诉和申诉。评论会显著增加网络暴力与审核成本，建议第二阶段再做。

### 4.6 管理后台（上线前 P0）

- 待审核内容队列和风险标签；
- 帖子、图片、用户、店铺检索；
- 举报 / 商家投诉 / 用户申诉工单；
- 隐藏、限流、打码、要求修改、删除、封禁和恢复；
- 原文与修改版本、审核人、操作时间、理由、证据附件的审计日志；
- 敏感词、严重指控词、频率限制和可信用户规则配置；
- 热点异常：同一店铺短时发帖/举报激增、新账号集群、同设备或同网络异常；
- 数据导出与依法协查流程。

## 5. 奖励机制

首版可以没有可兑换奖励，但应有轻量贡献反馈。推荐“贡献分 + 徽章”，不做现金、红包、免费提现或商家赞助的负面任务。

可加分：

- 首次完成信息完整的亲历记录；
- 补充到店时间、价格和有效凭证；
- 一段时间后确认“仍有效”或主动标记“情况已改善”；
- 举报经审核确认有效；
- 内容被不同真实用户标记“有帮助”，但设每日上限和反作弊；
- 收到争议通知后及时补充证据或纠正错误。

不得加分：

- 单纯选择“谨慎选择”；
- 负面用词更激烈；
- 同一店铺重复发帖；
- 帖子的曝光、争吵或举报数量；
- 邀请他人集中评价某家店。

徽章示例：城市记录者、夜市观察员、价格标注达人、认真纠错者。排行榜若保留，只按“有效贡献”且由用户主动选择公开；不设置“避雷王”“最差餐厅猎人”等称号。

## 6. 数据模型草案

### 6.1 核心实体

- `Place`：名称、城市、行政区、商圈、地址、经纬度、POI 来源及 ID、营业状态、合并关系。
- `VisitRecord`：用户、地点、到店日期、结论、消费区间、等待时间、正文、可见范围、审核状态、风险等级、当前版本。
- `RecordTag`：价格、服务、口味、排队、卫生观感、宣传不符等结构化标签。
- `RecordMedia`：图片、脱敏状态、内容安全结果、原文件受限地址。
- `Evidence`：消费凭证类型、受限文件、核验状态；默认不公开。
- `HelpfulVote`：用户与帖子唯一关系、反作弊信息。
- `Report`：举报人、对象、类型、说明、附件、处理状态。
- `MerchantClaim`：商家主体、店铺关系、认证材料、审核状态。
- `AppealCase`：权利投诉、转通知、用户声明、平台决定、期限。
- `ModerationAction`：操作对象、前后状态、操作人、理由和时间。
- `UserTrust`：实名状态、账号年龄、发布限额、违规次数、可信等级。

### 6.2 隐私设计

- 发布者前台使用昵称；后台保存依法需要的身份核验结果，严格限制访问。
- 仅保存实现服务和履行法定义务所需的信息，明确保存期限和删除规则。
- 精确定位只用于用户主动选店；公开内容展示店铺位置，不展示用户定位采集时间、家庭/工作地点或移动轨迹。
- 图片发布前做人脸、车牌、电话、订单信息检测与遮挡。
- 修改隐私政策，逐项说明定位、相册/相机、手机号、内容、凭证的目的、方式、范围和保存期限。

## 7. 内容规则摘要

允许：

- “2026 年 8 月晚餐到店，菜单标价 38 元，结账为 42 元；我询问后店员解释另收餐具费。”
- “等位约 50 分钟，超过我能接受的时间，赶时间的人谨慎选择。”
- “这道菜对我来说过咸，个人不会复购。”

需要修改或举证：

- “这家就是黑店 / 骗子 / 全是预制菜 / 吃了一定中毒。”
- “听朋友说老板人品有问题。”
- 发布店员姓名、私人电话、正脸并号召网友围攻。

平台提示语不应替代审核。即使用户勾选“内容由用户负责”，运营方在收到通知或已经知道风险后仍需采取措施。

## 8. 合规清单与风险等级

### P0：没有就不建议开放公开发布

- 核对小程序主体类型、ICP备案和微信实际服务类目；UGC 功能与申报类目一致。
- 发布者真实身份认证；浏览与写入均需登录并通过 Redis 会话校验。
- 文本、图片内容安全接口 + 自有风险规则 + 人工审核队列。
- 醒目的举报入口、权利投诉入口、申诉与结果反馈。
- 用户协议、社区公约、隐私政策和内容审核规则更新并重新取得必要同意。
- 投诉通知—转送—声明—恢复/删除流程，以及证据和操作日志保存。
- 账号限频、封禁、黑名单和异常热点处置。
- 店员/顾客个人信息、人脸、订单凭证默认脱敏。
- APP/小程序备案信息、名称、简介和实际功能同步变更。

### P1：公测前完成

- 商家认领与公开回应；回应也要审核，不得曝光消费者个人信息。
- 内容时效提示和“情况已改善 / 信息过时”机制。
- 地图 POI 数据来源和授权条款核对。
- 未成年人保护与客服值守方案。
- 内容安全事件预案、审核 SLA、节假日值班与依法协查联系人。

### 高风险、首版不做

- “全国最坑餐厅”“城市黑榜”等纯负面榜单；
- 评论、私信、群组、匿名投稿、隔空喊话；
- 现金悬赏曝光、按阅读量奖励差评；
- 商家付费删帖、充值压负面或暗改排序；
- 转载其他平台差评、搬运商家图片或聚合未经核实的爆料；
- 通过爬虫采集小红书、抖音等平台的评价、图片或视频，再以虚构昵称、平台账号或“网友评价”形式发布；
- 对爬取内容进行 AI 改写、摘要或去除原作者信息后，当作本站原创或用户亲历内容发布；
- 自动用 AI 生成对具体商家的负面结论；
- 对疾病、食安违法作无依据的确定性判断。

## 9. 已确认的产品方案

当前决定采用：**个人主体 + 具体餐厅点评 + 全量先审后公开**。

首版公开评论必须同时满足：绑定到具体餐饮地点、来源于本人到店足迹、通过文本和图片检测、进入人工审核、审核通过后才可被其他用户访问。首版不采用“低风险自动直发”，所有评论统一进入 `pending`。

发布流程调整为：

`保存私人足迹 → 创建评论快照 → 内容安全检测 → 人工审核 → 公开`
`人工驳回 → 告知具体原因 → 用户再次到店或后续评论编辑流程处理`

用户应始终可以只保存私人足迹。饮食识别产生的私人记录不参与此流程。公开帖首版不开放评论、私信、关注、话题和转发动态流。

## 10. 是否需要重新备案

### 10.1 明确结论

需要办理**小程序备案信息变更**，通常不需要注销原备案后重新申请，也不需要更换 AppID 或重新注册一个小程序。

原因是本项目从“AI 营养分析 / 健康管理”改为“餐饮点评与推荐”，实际服务内容和类目发生实质变化；如果同时更换 NutriLens 名称、图标和简介，备案中的应用名称、图标、类目及服务信息也会变化。工信部要求 APP/小程序备案信息发生变化时向原备案机关办理变更，备案表中的应用名称、图标和类目应与实际情况一致。

按以下情况处理：

| 当前情况 | 应做事项 |
|---|---|
| 已有有效小程序备案，同一 AppID、同一个人主体 | 办理“变更备案/变更服务信息”，不要先注销 |
| 从未完成小程序备案 | 提交首次备案，通过后才能上线新版 |
| 只改代码、但名称和备案服务内容仍写营养健康 | 仍应变更，因为备案内容已与实际业务不符 |
| 更换为新的个人主体 | 不能当普通信息修改处理，需按平台的主体迁移或新主体备案流程办理 |
| 将来改成个体工商户/企业 | 再评估主体迁移和新主体备案；本期不需要为了窄版餐饮点评立即更换主体 |

小程序备案与后端域名的 ICP 备案是两件相关但不同的事项：

- **小程序备案**：通过微信公众平台办理，关联 AppID、主体、名称、类目和服务内容。本次必须变更。
- **网站/域名 ICP 备案**：如果现有后端域名、主办者、接入商和网站用途信息都没有变化，一般不因前端改版而重新备案；如果域名备案中的网站/服务名称或内容仍明确写“营养健康”，或更换域名、主体、接入信息，则联系接入服务商办理相应变更。
- 小程序备案表对小程序通常不要求填域名和公钥，但实际使用的请求域名仍必须合法备案并配置在微信后台服务器域名白名单。

备案是否保留原编号、审核期间是否影响线上旧版本，以微信备案页面和所在地通信管理局的实际处理结果为准；不要自行注销现有备案。

### 10.2 建议操作路径

微信公众平台的菜单名称可能调整，按相同含义寻找即可：

1. 登录 [微信公众平台](https://mp.weixin.qq.com/)，确认管理员、个人主体信息、现有备案号和备案状态。
2. 进入“设置 / 基本设置 / 服务类目”，确认当前账号可添加 **餐饮—点评与推荐**。这是继续开发公开版的前置门槛。
3. 确定新名称、简称、头像和简介，先完成微信侧名称修改审核。名称不要使用“黑店、曝光、维权、投诉、官方、全国”等高风险或可能受限词。
4. 添加“餐饮—点评与推荐”服务类目；删除不再实际提供且可能造成审核误判的旧健康/AI类目。
5. 在微信公众平台的“小程序备案”入口选择“变更备案”或“变更服务信息”，同步新名称、图标、类目和服务内容。服务内容建议如实写为：**提供个人到店餐饮体验记录、经审核的餐饮点评与推荐信息展示，不提供点餐、外卖、团购、交易及通用论坛服务。**
6. 按页面要求完成负责人核验、材料提交和工信部短信核验；收到 12381 验证短信时应在提示期限内完成核验。
7. 备案变更通过后，核对小程序详情页展示的名称、主体、类目和备案编号是否一致。
8. 完成下列隐私、协议和内容治理改造后再提交代码审核，不要先上线公开发布、后补审核后台。

如果第 2 步后台没有“餐饮—点评与推荐”，或类目审核明确拒绝个人主体，则停止公开版提审：保留私人餐饮记录功能，或者再注册/迁移到个体工商户或企业主体。不得用“工具—信息查询”“备忘录”等类目包装公开点评。

## 11. 必须同步变更的微信配置和产品材料

### 11.1 名称、图标与介绍

现有 `NutriLens / 营养镜头 / AI 智能饮食分析` 与新业务明显不符，建议全部更换。新名称尚未确定，需求和代码暂用 `[新产品名]` 占位。

名称方向示例仅供讨论，使用前需检查微信重名、商标和备案命名限制：`食迹簿`、`城味实录`、`这顿记一下`。不建议名称直接使用“避雷、黑榜、曝光、维权、投诉”。

简介建议：

> 记录真实到店餐饮体验，查看经审核的价格、口味、排队与服务信息。

代码中至少需要同步替换：`manifest.json` 名称和描述、`pages.json` 全局标题、登录页、关于页、分享文案、分享海报以及所有营养/AI宣传语。

### 11.2 服务类目

- 主类目目标：`餐饮—点评与推荐`，最终以该个人账号后台当日可选项为准。
- 首版不申报也不提供：社交社区/论坛、点餐平台、外卖平台、团购交易、互联网新闻、医疗健康。
- 页面、接口、隐藏入口和提审版本代码都不能残留与申报类目不符且仍可访问的功能。

### 11.3 小程序用户隐私保护指引

现有指引和页面仍描述身高、体重、年龄、性别、食物照片及 AI 营养分析，必须重写并在微信后台“用户隐私保护指引”中同步更新。新版按实际使用声明：

- OpenID、昵称和头像：账号识别与公开作者信息；
- 经验证的手机号：公开发布者身份核验、投诉联系和账号安全，仅后台使用，不公开；
- 用户选择的位置信息 / 地图 POI：选择餐厅和展示店铺位置；
- 用户选中的照片：发布到店图片、凭证审核和内容安全检测；
- 用户输入的文本：形成私人记录或经审核公开的餐饮点评；
- 设备、网络、操作日志：安全风控、违规处置和投诉证据留存；
- 第三方处理者：微信、地图/POI、对象存储、内容安全等实际服务商及处理目的；
- 保存期限、用户查询/更正/删除/撤回同意/注销方式和有效联系方式。

位置、相册/相机、手机号等能力必须先在微信隐私指引中准确声明，并在用户触发相应功能时请求授权；拒绝非必要权限的用户仍应能浏览公开内容和手动选择城市。

### 11.4 用户协议与社区规则

现有用户协议需要替换营养分析条款，并新增：

- 仅发布本人亲历、保证事实部分真实；
- 事实陈述与主观感受的表达要求；
- 禁止侮辱、诽谤、威胁、隐私曝光、虚假交易和同行恶意评价；
- 消费凭证仅用于审核，默认不公开；
- 平台审核、要求修改、限流、隐藏、删除和封禁规则；
- 商家/权利人通知、用户不侵权声明和申诉流程；
- 内容授权仅限提供、展示和维护本服务所必要的范围；
- 用户删除内容、注销账号及法定留存例外；
- 投诉举报联系方式和处理流程。

“继续使用即视为同意更新”不能替代重大目的变化所需的重新告知和同意。老用户首次进入新版时，应展示新版本协议并重新确认；未同意的用户可查看旧数据、删除数据或注销，但不能发布。

### 11.5 旧数据处理

- 现有饮食、健康和 AI 分析数据不得自动转换成公开餐饮评价，也不得因新业务直接用于推荐或画像。
- 上线前决定是保留一个限时只读入口，还是通知用户后删除旧饮食数据；无论选择哪种，都要写明期限和删除方式。
- 身高、体重、年龄和性别不再是新服务必要信息，应停止新增收集，并提供删除路径。
- 旧积分不要直接变成公开“可信度”。建议保留为历史荣誉或清零后启用新的贡献分，并提前告知。
- 旧版 AI 食物分析、饮食历史、“今天吃什么”、自定义菜品、积分、成就、连续打卡、排行榜和分享海报可统一收纳到“我的—旧版数据与工具”，作为冷启动阶段的可用工具，但不进入新版公开点评的信息流。

### 11.6 接口、权限和第三方服务

- 接入微信文本、图片/音视频内容安全能力，服务端保存检测结果；不能只靠前端敏感词。
- 新增地图/POI 服务并核对个人开发者准入、调用额度、数据展示和缓存授权。
- 在微信后台配置新的 request/upload/download 合法域名；如域名不变只需复核，不必为改版另换域名。
- 如原订阅消息模板是三餐/健康提醒，应停用并重新申请与新业务一致的模板；不能改文案继续套用不相符模板。
- 不需要微信支付；首版不接交易、充值、打赏和现金奖励。

### 11.7 安全整改

当前仓库配置中存在不应提交到代码库的服务密钥和凭证。公开测试前必须全部轮换，将真实密钥移入环境变量或密钥管理服务，清理版本历史中的暴露值，并限制数据库、对象存储和审核后台权限。此项列为上线阻断项。

## 13. 实施顺序

1. **准入确认**：先在微信后台验证个人主体类目，不通过就不开发公开社区能力。
2. **品牌确认**：确定新名称、图标、简介，检查重名和商标风险。
3. **平台变更**：修改名称和服务类目，提交小程序备案信息变更。
4. **合规设计**：定稿隐私政策、用户协议、社区规则、投诉申诉规则和旧数据方案。
5. **安全先行**：轮换仓库中已暴露的密钥，建设审核后台和紧急开关。
6. **零数据可用版本**：先完成合法 POI 店铺资料、搜索、私人记录、足迹、收藏、“吃什么”和旧版工具入口，确保没有公开内容时产品仍可使用。
7. **真实内容供给**：运营人员完成实地记录，招募少量体验官，建立首发商圈的真实种子内容。
8. **公开能力开发**：完成先审后发、发现、举报申诉、贡献分和来源标识。
9. **联调验收**：内容安全、隐私授权、身份核验、地图、图片脱敏和审核留痕。
10. **提交审核**：提供清晰测试路径，确保审核人员可以看到待审核状态、来源标识与内容治理能力。
11. **灰度运营**：先开放一个城市中的少数商圈和有限用户，每日发布限额，人工复盘所有投诉。

## 14. 分阶段路线图

### 阶段 1：受控公开 MVP

- 合法 POI 店铺基础资料、店名搜索和附近店铺；
- 私人草稿和公开申请；
- 城市 / POI、到店日期、标签、图片、足迹和搜索；
- 收藏、从附近或收藏中抽选“吃什么”、分享个人足迹卡片；
- 旧版数据与工具的私人入口；
- 所有公开申请先经机器检测和人工审核；
- 发现页仅展示审核通过内容；
- 举报、权利投诉、用户申诉和紧急隐藏；
- 一个城市少数商圈灰度，每个新用户设每日发布上限；
- 公开供给未达到阈值时，发现页以搜索、工具和个人记录为主，不制造虚假信息流。

### 阶段 2：可信点评

- 商家认领与结构化回应；
- 可信记录者、内容版本和“情况已改善”；
- 贡献分和少量非现金徽章；
- 根据运营数据完善反作弊和审核策略。

### 阶段 3：暂不承诺

- 评论、关注等功能只有在主体、服务类目和审核能力允许时再评估；
- 附近推荐和个性化排序上线前另做算法与隐私合规评估；
- 若产品需要发展成真正社区，优先迁移至个体工商户或企业主体并重新核对资质。

## 15. 冷启动与首批内容策略

### 15.1 冷启动目标

冷启动不以“看起来像一个已经成熟的社区”为目标，而以“一个商圈内已经有用、没有公开内容也能独立使用”为目标。产品采用以下顺序建立价值：

`合法店铺资料 → 私人记录工具 → 真实种子内容 → 分享带来新用户 → 新用户产生更多真实记录`

首发范围建议控制在一个城市的 2～4 个相邻商圈。运营资源优先用于提高局部店铺与体验密度，不为扩大城市数量而复制低质量内容。

### 15.2 零内容状态

当公开体验数量为零或很少时，小程序仍提供：

- 按店名、小吃名和商圈搜索合法 POI 店铺资料；
- 查看附近店铺和基础营业信息；
- 创建仅自己可见的到店记录、足迹地图和收藏；
- 从附近店铺、收藏和自定义菜品中抽选“今天吃什么”；
- 使用旧版 AI 食物分析、饮食历史和个人成长记录；
- 生成个人餐饮足迹卡、月度回顾和单店体验卡用于微信分享。

没有体验的店铺必须显示真实空状态，例如“暂无真实体验，记录第一条”。不得伪造“热门”“已有多人推荐”“最近很多人来过”等社会证明。

### 15.3 首批店铺与内容来源

首批供给建议采用以下组合：

1. 从获得授权的地图 / POI 服务导入 100～300 家店铺基础资料，只使用许可范围内的字段和缓存方式；
2. 运营人员真实到店，自行拍摄和撰写 30～50 条“编辑实地记录”；
3. 招募约 20 名本地体验官，每人提交 3～5 条本人真实经历，目标补充 60～100 条记录；
4. 允许用户主动导入其本人在其他平台发布的原创内容，但需确认其作者身份与授权，并按本站规则重新提交和审核；
5. 允许商家提交菜单、价格、营业时间、环境图片和预约说明，统一标记“商家提供”，不得冒充消费者评价。

体验官激励只与信息完整度、凭证有效性、及时纠错和持续更新有关，不与好评、差评、曝光量或负面程度挂钩。若提供补贴或其他利益，应在内容来源或规则中如实说明。

### 15.4 禁止的数据填充方式

- 不爬取或搬运小红书、抖音、大众点评等平台的评价、图片和视频填充本站；
- 不把爬取内容套在虚构昵称、虚构头像或批量注册账号下发布；
- 不虚构到店日期、价格、排队时间、菜品、凭证或总体结论；
- 不通过 AI 洗稿、摘要或拼接多条内容来伪装成新的真实体验；
- 不把商家宣传材料展示为用户体验；
- 不将开发、演示或提审数据接入正式生产环境。

开发和提审环境可以使用完全虚构的店铺与记录，但应具有 `is_demo` 标识、醒目标注“演示数据”，使用与真实商家不混淆的名称，并与生产数据库、搜索索引、统计指标和分享链路隔离。

### 15.5 分享增长闭环

首版增长重点不是转发公共差评，而是分享用户自己的记录成果：

- 单店体验卡：本次到店时间、价格、标签和个人结论；
- 城市 / 商圈足迹图：用户去过的店铺和记录数量；
- 月度餐饮回顾：本月新店、常去品类和个人收藏；
- “今天吃什么”结果卡：从附近或收藏中抽中的店铺。

分享落地页优先展示对应店铺或足迹内容，并提供“收藏这家店”“记录我的体验”“生成我的足迹”等低门槛动作，形成：

`记录 → 生成卡片 → 微信分享 → 好友查看 / 收藏 → 创建自己的记录`

分享文案不得号召围攻、集中差评或抵制具体商家。

### 15.6 公开发现页开放阈值

建议满足以下内部条件后，再把公开体验信息流提升为发现页主内容：

- 首发商圈累计至少 100 条审核通过的真实记录；
- 至少 50 家店铺拥有一条公开体验；
- 至少 20 名非运营账号产生有效记录；
- 举报、商家投诉、用户申诉和紧急隐藏链路已经实测；
- 所有种子内容均可追溯到真实发布者、原始图片、到店时间和审核记录。

阈值未达到时，可以开放搜索和单店详情，但发现页继续以工具、个人足迹和少量明确标记的编辑记录为主。

## 16. 成功指标

北极星指标：**每周被再次查看或被标记有帮助的有效到店记录数**。

辅助指标：

- 记录完成率、平均填写时长；
- 含到店日期 / 价格 / 图片 / 凭证的完整记录比例；
- 7 日和 30 日记录者留存；
- 每百条内容举报率、确认违规率；
- 举报首次响应时间、投诉结案时间；
- 被纠正后主动更新率；
- 同店异常集中发帖率和虚假内容漏审率。

不以“负面帖子数”“被投诉商家数”作为增长指标。

冷启动阶段额外观察：

- 首发商圈有公开体验的店铺覆盖率；
- 非运营用户产生的真实记录占比；
- 空店铺详情到“记录第一条”的转化率；
- 足迹卡、月度回顾和单店体验卡的分享打开率；
- 分享访问到收藏 / 创建记录的转化率；
- 导入本人原创内容的授权完整率和审核通过率。

## 17. 尚待产品负责人确认

1. 新产品名称、图标和简介；
2. 首发城市；
3. 人工审核负责人、工作时段和对用户承诺的审核时效；

9. 公开发现页达到什么数据阈值后切换为信息流优先。

## 17.1 个人主体版本的产品边界

个人主体并非完全不能做餐饮点评。可行路径是以“餐饮-点评与推荐”为目标类目，提供围绕具体餐厅、小吃的结构化消费评价和信息展示，而不是把产品做成通用发帖社区。

个人主体 MVP 建议保留：

- 用户选择具体餐厅或小吃地点后提交一次到店记录；
- 到店日期、消费区间、口味、价格、排队、服务等结构化字段；
- 仅自己可见的私人记录；
- 经平台先审后公开的餐饮点评；
- 店铺搜索、城市筛选、“有帮助”、举报和纠错；
- 后台可追溯的登录用户，不开放匿名投稿。

个人主体 MVP 建议删除或延后：

- 评论、楼中楼、私信、关注、粉丝、群组和话题社区；
- 用户自由发布与餐饮无关的图文动态；
- “曝光台”“黑店榜”“全城避雷榜”等聚集攻击性的页面；
- 用户主页动态流、转发扩散、号召抵制；
- 商家入驻交易、点餐、团购、广告竞价和付费删帖；
- 现金奖励、红包奖励和按负面内容流量发奖。

建议在开发前先完成一个零代码门槛验证：登录微信公众平台，在“设置 > 基本设置 > 服务类目”中尝试添加“餐饮-点评与推荐”。若当前账号后台没有该选项，或类目审核明确要求非个人主体，就只发布“私人餐饮足迹本”，不要用工具、信息查询等不相符类目包装公开点评功能。最终能否过审以账号后台当日规则和实际代码审核为准。

## 18. 主要依据

- [《移动互联网应用程序信息服务管理规定》](https://www.cac.gov.cn/2022-06/14/c_1656821626455324.htm)：信息发布用户真实身份认证、内容审核、日常巡查、投诉举报和平台上架管理。
- [《中华人民共和国民法典》网络侵权责任相关条款](https://www.cac.gov.cn/2020-06/01/c_15925617772683196.htm)：第一千一百九十四条至一千一百九十七条的通知、声明、必要措施与责任规则。
- [《网络暴力信息治理规定》](https://www.cac.gov.cn/2024-06/14/c_1720043894161555.htm)：信息发布审核、风险预警、评论/论坛治理、快捷投诉举报和证据保存。
- [《中华人民共和国个人信息保护法》](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)：最小必要、告知同意、保存期限和行踪轨迹等敏感个人信息规则。
- [工业和信息化部关于开展移动互联网应用程序备案工作的通知](https://www.gov.cn/zhengce/zhengceku/202308/content_6897341.htm)：备案范围明确包含小程序。
- [工业和信息化部《互联网信息服务备案登记表》](https://xzca.miit.gov.cn/bsfw/bszn/art/2024/art_5d3cc7f452c04fdd97b6881a20b656f9.html)：备案中的应用名称、图标、类目等应如实填写，变更后及时更新。
- [腾讯云“变更备案”说明](https://cloud.tencent.com/document/product/243/37406)：已有备案服务的信息发生变化时办理变更，不等同于先注销重办。
- [腾讯云小程序隐私保护指引适配说明](https://cloud.tencent.cn/document/product/1301/97930)：个人信息类型和隐私接口调用变化时应更新微信后台指引并取得用户授权。
- [最高人民法院企业名誉权司法保护典型案例](https://www.court.gov.cn/zixun/xiangqing/455051.html)：未经实际测评、缺乏事实依据的负面测评可能侵害企业名誉权。
- [最高人民法院网络消费典型案例](https://www.court.gov.cn/zixun/xiangqing/393481.html)：消费者批评权受保护，同时商家回应差评不得侵犯消费者隐私与个人信息。
- [腾讯微信小程序平台侵权投诉指引](https://ipr.tencent.com/complain?id=8)：微信侧存在针对小程序内容的正式权利投诉渠道。
- [《互联网信息服务算法推荐管理规定》](https://www.cac.gov.cn/2022-01/04/c_1642894606364259.htm)：后续若使用个性化推送、排序精选等算法，应另行落实透明、用户选择和内容治理义务。

微信服务类目和资质会动态调整，提审前必须以小程序管理后台当日展示及微信审核反馈为准，不能只依赖历史截图或第三方文章。
