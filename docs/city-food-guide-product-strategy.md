# 食迹簿：首页与城市美食攻略产品策略

> 状态：核心定位已确认，首页视觉与交互仍待验证  
> 版本：0.2  
> 更新日期：2026-09-11  
> 本轮范围：产品定位、用户留存、认真记录机制、首页信息架构、攻略内容来源与合规边界。暂不确定最终视觉稿，不调整代码。

## 1. 这次需要先解决的问题

当前首页的问题不只是“颜色不好看”，而是产品主次不清：

- 用户第一眼看不出这是餐厅点评、个人记录工具，还是旅游攻略。
- 长期功能和短期活动使用了近似的视觉权重。
- 首页把推荐结论、价格、排队等记录字段直接摊开，却没有回答用户真正关心的“我现在应该怎么吃”。
- 内容量不足时依靠大图和卡片装饰撑版面，容易显得像模板，也无法建立稳定的产品辨识度。
- 要求用户认真记录，但没有先给用户足够价值，也没有把记录动作放进真实用餐场景。

因此，首页设计之前必须先回答：**食迹簿究竟替用户完成什么任务？**

## 2. 产品定位

### 2.1 一句话定位

**食迹簿是一份城市隐秘饮食地图：带用户走进街巷、市场和社区，吃到当地人真实日常，也在旅程结束后形成个人吃喝档案。**

它不应成为另一个按评分排序的餐厅点评平台，不以“附近最多”“全城最热”或“避雷”为主要心智，也不与美团、大众点评竞争全量 POI 和实时交易数据。

### 2.2 核心承诺

用户打开食迹簿，不只获得“去哪家店”的答案，还应获得：

1. 为什么值得去。
2. 什么时候去更合适。
3. 先去哪家、后去哪家。
4. 每一站吃什么、预计停留多久。
5. 步行或交通如何衔接。
6. 计划失效时有什么附近替代方案。

攻略的最小单位不是“餐厅”，而是**可以实际执行的一段吃喝行程**。

### 2.4 已确认的内容主题

首页和路线内容优先寻找：

- 居民区、菜市场、老街和小巷里的日常饮食。
- 本地人长期消费、网络曝光较少的小店和摊档。
- 只认真做少数几样食物、有稳定手艺的经营者。
- 能解释地方物产、生活节奏和饮食传统的具体食物。
- 不依靠打卡布景和流量营销，却值得专门走一段路去吃的地方。

“曝光少”只是发现线索，不等于正宗或优质。正式收录必须经过实地核验、多个来源交叉确认，并记录最后核验时间。

### 2.3 三层产品关系

| 层级 | 用户价值 | 产品模块 | 是否长期 |
|---|---|---|---|
| 出发前 | 降低做攻略成本 | 城市路线、场景攻略、收藏与行程安排 | 长期核心 |
| 用餐中 | 降低临场决策成本 | 路线导航、到站提示、替代店、快速事实反馈 | 长期核心 |
| 用餐后 | 保存记忆并改善内容 | 到店记录、足迹、私人营养记录 | 长期核心 |
| 阶段话题 | 提供参与理由和内容主题 | 城市征集、节令专题、联合活动 | 短期运营 |

活动只是加速器，不能替代核心产品。

## 3. 最重要的用户

### 3.1 第一目标用户：旅行中的吃喝规划者

典型状态：

- 第一次或短期来到一座城市。
- 可用时间有限，常见窗口为两小时、半天或一天。
- 在多个平台收藏了大量餐厅，却不知道距离、顺序和时间是否合理。
- 害怕排很久、临时闭店、跨区折返，也担心网红店并不适合自己的同行人。

核心任务：

> 我有半天时间，在当前区域附近，想吃到这座城市有代表性的几样东西，请直接给我一条走得通的路线。

### 3.2 第二目标用户：本地持续探索者

典型状态：周末想换个街区、下班想顺路吃饭、愿意收藏主题路线，但不会每天主动写长点评。

核心任务：

> 不要再给我一张泛泛的榜单，给我一个今天就能执行的新吃法。

### 3.3 第三目标用户：愿意留下真实记录的人

他们是内容更新的重要来源，但不应被当成免费的内容生产机器。只有先获得路线、档案或归属感价值，才有持续贡献的理由。

## 4. 用户为什么会留下来

留存不能只依赖每天刷新推荐流。食迹簿应建立三种回访理由。

### 4.1 任务型留存：一次旅行要多次打开

完整链路：

```text
发现路线 → 收藏或调整 → 到达城市 → 开始行程 → 逐站完成 → 保存足迹 → 旅后回顾
```

同一条路线天然产生出发前、用餐中、用餐后的多次访问，比单次阅读餐厅帖子更有价值。

### 4.2 资产型留存：用户带不走的个人档案

用户长期积累：

- 去过的城市、街区和店。
- 完成过的路线。
- 自己写下的菜品与感受。
- 私人营养识别历史。
- 收藏但尚未完成的路线。

重点不是积分数字，而是“这是我的吃喝地图”。

### 4.3 内容型留存：信息会过期，也会变新

用户回访的内容理由应是：

- 新城市、新街区路线。
- 季节限定和节令吃法。
- 已收藏路线的营业状态、顺序或替代店发生变化。
- 来自真实到访者的最新事实更新。

不建议用无意义的签到、连续打卡或夸张红点制造虚假活跃。

## 5. 怎么让用户愿意认真记录

### 5.1 先降低“认真”的成本

认真记录不等于一开始就填写完整表单。更合理的方式是分阶段采集：

#### 到店当下：10 秒内完成

- 到过 / 没吃上 / 已闭店。
- 实际等候时间。
- 点过哪些菜。
- 价格区间或人均。
- 一张现场照片，可选。

这些信息客观、短、对下一位旅行者直接有用。

#### 离店之后：30～60 秒补充

- 哪道菜值得专程吃。
- 哪类同行人更适合。
- 如果重来，会不会调整点单或时间。
- 一句自由感受。

#### 当天晚上或旅程结束：形成回顾

系统把路线完成情况、照片、菜品和事实字段整理成草稿，由用户修改和确认。AI 只能整理，不得替用户虚构体验。

### 5.2 让记录立即产生回报

每次记录完成后，不只显示“提交成功”，而应立刻反馈：

- 个人路线图点亮了一站。
- 今天的吃喝行程形成一页可回顾的行程单。
- 该事实帮助系统更新了“建议到店时间”或“近期排队情况”。
- 用户可以保存一张克制、真实的旅行回顾卡片。

### 5.3 区分事实、感受和系统推断

| 类型 | 示例 | 处理方式 |
|---|---|---|
| 用户事实 | 周六 11:20 到店，等了 18 分钟 | 可结构化、带日期展示 |
| 用户感受 | 汤底对我来说偏咸 | 明确归属于个人，不包装成客观结论 |
| 系统汇总 | 近 30 天周末午间常需等位 | 标注样本数、时间窗口和更新时间 |
| 外部来源 | 某创作者介绍的点单方法 | 展示来源和授权/引用关系 |

“真实”不是让用户打一个推荐或差评，而是让信息可追溯、有时间、有语境。

## 6. 首页应该讲清楚什么

首页需要在五秒内回答四个问题：

1. 这是什么：城市吃喝路线工具。
2. 能做什么：找路线、排顺序、边走边吃、保存足迹。
3. 现在最重要的动作是什么：选择城市和可用时间，开始找一条路线。
4. 为什么可信：来源透明、更新时间明确、真实到访者持续校正。

### 6.1 功能权重建议

| 首页内容 | 建议权重 | 原因 |
|---|---:|---|
| 可执行的城市美食路线 | 40% | 最核心差异和旅行用户的首要任务 |
| 按时间/区域/同行人找吃法 | 20% | 帮用户迅速缩小选择 |
| 新发现的小巷、市场与社区路线 | 15% | 强化产品独有的城市内容 |
| 最近实地核验与店铺变化 | 10% | 建立内容活性和可信度 |
| 征集与阶段活动 | 不超过 10% | 提供参与感，但不能抢主功能 |

不再把“推荐 / 一般 / 谨慎选择 / 价格 / 排队”作为首页频道。它们只能在路线详情或单店信息中辅助决策。

### 6.2 首屏建议

首屏不使用泛化口号或纯装饰大图，而是一个可直接开始的任务：

```text
[当前城市：上海]

今天有多少时间？
[2 小时] [半天] [一天]

从哪里开始？
[当前位置] [选择街区/景点]

[帮我安排一条吃喝路线]
```

下面可以紧接一条编辑精选路线，但必须展示执行信息：时间、步行距离、站数、预算、更新时间，而不是只展示漂亮封面。

### 6.3 建议的信息顺序

1. 城市与任务入口。
2. 今日/本周精选可执行路线。
3. 按旅行场景找路线：第一次来、亲子、雨天、夜宵、一个人、长辈同行等。
4. 新近走访的小巷、市场与社区路线。
5. 最近被核实或更新的信息。
6. 当前征集活动。
7. 产品可信原则与内容来源说明。

“附近现在能吃什么”不进入当前核心范围。该能力需要大规模、实时的 POI、营业、距离、排队和交易数据，现阶段无法形成可信优势。首页只展示带明确核验日期的路线与店铺信息，不承诺实时营业状态。

## 7. 城市美食攻略的数据结构

一条真正有价值的攻略至少包含以下内容。

### 7.1 路线级信息

- 标题：说明区域、时间和体验，不写空泛“必吃榜”。
- 适合人群：第一次来、亲子、一个人、长辈、夜间等。
- 总时长、总距离、交通方式、预算范围。
- 建议开始时间和不建议开始的时间。
- 最近核验日期和变化提醒。
- 雨天、高温或店铺临时关闭时的替代策略。
- 内容作者、编辑者、事实来源和商业合作标记。

### 7.2 每一站信息

- 建议到达时间和停留时长。
- 推荐点单及建议份量。
- 为什么放在这一站，和前后站如何衔接。
- 常见等待情况，但必须带采样时间，不能作为永久标签。
- 从上一站步行/交通所需时间。
- 备选店及切换条件。
- 信息来源、最后确认时间。

### 7.3 路线示例

> 不是“上海面馆 Top 10”，而是“从人民广场出发的 3 小时老城厢早餐路线”：08:00 小笼，08:50 步行 12 分钟吃汤团，09:40 逛市场消食，10:30 以一碗小馄饨收尾；同时给出周一闭店替代和雨天缩短方案。

## 8. 攻略内容从哪里来

建议使用四层内容体系。

### 8.1 自有编辑路线

初期质量最高、最可控。编辑根据实地体验、商户公开信息和多来源核验写成原创路线。必须保留内部来源记录和核验日期。

收录标准不是“流量低”，而是至少满足以下多数条件：

- 有稳定的本地日常客群，而非主要依赖一次性打卡客流。
- 招牌食物和制作方式长期稳定。
- 与所在街区、市场或地方饮食传统存在真实联系。
- 价格、份量和接待能力适合被推荐给旅行者。
- 经营主体和地点信息可以核验，不以未经证实的传奇故事包装内容。
- 公开推荐不会明显扰乱居民生活或超过小店正常接待能力。

### 8.2 授权创作者路线

邀请本地创作者或旅行 UP 主授权，将其经验重新组织成可执行路线：

- 明确展示创作者名称、头像和原平台主页/作品链接。
- 书面约定允许使用的文字、图片、视频封面和期限。
- 区分“联合创作”“经授权整理”“仅引用观点”。
- 创作者撤回授权时有下架或替换流程。

这是展示“来自某某 UP 主”最稳妥、也最有品牌价值的方式。

### 8.3 用户亲历更新

用户不需要创作整条攻略，只补充某一站的近期事实：是否营业、排队多久、菜品是否售罄、价格变化。达到一定可信度后由编辑或规则系统更新路线。

### 8.4 商户事实信息

营业时间、地址、菜单、预约方式可以来自商户认领或公开登记，但必须明确这是“商户提供”，不能与独立体验混为一谈。

## 9. 能不能爬小红书、抖音

### 9.1 产品结论

**不建议把未经授权的自动抓取作为正式内容供给方案。仅注明“来自某某 UP 主”并不等于取得使用许可。**

风险不只来自爬虫技术本身，还包括：

- 原文、图片、视频和封面可能受著作权及信息网络传播权保护；重新展示、改写或汇编不当然因标注来源而合法。[《中华人民共和国著作权法》](https://www.npc.gov.cn/zgrdw/huiyi/cwh/1113/2010-02/26/content_1545222.htm)
- 规避登录、风控、验证码或其他技术措施批量取得平台数据，可能触及平台协议和反不正当竞争风险。现行反不正当竞争法明确规制以不正当方式获取、使用其他经营者合法持有的数据。[《中华人民共和国反不正当竞争法》](https://www.spp.gov.cn/tt/202506/t20250627_699860.shtml)
- 昵称、头像、位置、账号关系等仍可能构成个人信息；“公开可见”不代表可以不受限制地批量收集和二次利用，处理应控制在合理范围内。[《中华人民共和国个人信息保护法》](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm?ivk_sa=1024320u)
- 自动采集不可避免地取得非必要或未依法取得同意的个人信息，依法还涉及删除或匿名化要求。[《网络数据安全管理条例》](https://app.www.gov.cn/govdata/gov/202409/30/520076/article.html)

### 9.2 平台能力的现实情况

- 抖音存在官方开放能力，但视频数据通常需要用户授权和权限申请，关键词视频搜索属于特殊权限，并非可以任意批量取得全站内容。[抖音开放平台权限说明](https://open.douyin.com/platform/resource/docs/accession-guide/type-and-permission)
- 小红书当前公开的开放授权范围主要是基础账号信息；读取用户笔记仍标记为规划中，不能把账号授权等同于已获笔记内容读取和转载权限。[小红书开放平台 Scope](https://openaccount.xiaohongshu.com/docs/scope)

### 9.3 推荐的安全路线

按优先级采用：

1. 与创作者直接签约或取得明确授权。
2. 使用平台正式开放 API，并严格遵循权限、授权范围和展示要求。
3. 只把外部链接作为编辑发现线索，人工核验后撰写独立、原创、可执行的路线内容。
4. 仅展示必要的短引述时标明作者和原始链接，并建立删除/投诉通道；不要搬运图片、视频、整段文案或批量镜像内容。
5. 不热链外部媒体，不绕过访问限制，不抓取评论和用户画像，不把外部平台内容用于训练或画像。

正式上线前仍应由熟悉平台数据与内容版权的律师审阅授权协议和内容流程。本节是产品风险判断，不替代正式法律意见。

### 9.4 商业合作必须单独标记

如果路线、餐厅露出或创作者内容存在付费、置换、返佣或购买链接，应让用户清楚辨认其商业性质。互联网广告应具有可识别性，体验分享附带购买方式等情形也可能需要显著标明“广告”。[《互联网广告管理办法》](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/fgs/art/2023/art_d93a579afd45413e8576e4623fab348f.html)

建议内容标签固定为：

- 编辑实地核验
- 用户近期更新
- 创作者授权内容
- 商户提供信息
- 商业合作 / 广告

## 10. 首页视觉方向原则

本轮不产出视觉稿，只确定避免继续“随意拼色”的规则。

### 10.1 统一隐喻

建议选择“城市折页地图 + 随身食单”作为唯一视觉母题，而不是杂志、AI 工具、点评 App、社交社区四种风格同时出现。

### 10.2 色彩层级

- 70%：温暖但克制的纸张底色和内容底色。
- 20%：深墨色或深绿，用于导航、核心按钮、路线状态。
- 10%：单一暖色强调，用于当前选择和关键行动。
- 活动可以使用强调色的浅阶，但不能每个卡片随机一种高饱和颜色。
- 状态色只表达状态，不承担装饰任务。

候选基线，不是最终视觉定稿：纸张 `#F3EFE6`、墨色 `#25231F`、深绿 `#385348`、朱砂 `#AD4A36`、活动金 `#C79C45`。最终需在真实页面和图片上统一验证。

### 10.3 字体与排版

- 中文标题建立稳定的字号、字重和行距体系，避免靠英文小标题制造“设计感”。
- 信息先按任务层级分组，再决定是否使用卡片；不能所有内容都装进圆角白卡。
- 路线时间轴、站点顺序和地图关系应成为核心视觉元素。
- 图片保持一致比例和色调，只展示真实地点、菜品或路线环境，不使用泛化美食素材图。
- 首页首屏只能有一个主按钮，短期活动不使用与主按钮相同的权重。

## 11. 建议的完整用户闭环

```text
选择城市和可用时间
  → 获得 3 条可执行路线
  → 查看顺序、预算、距离和更新时间
  → 收藏 / 替换其中一站
  → 到达后开启“跟着吃”
  → 每站快速确认事实
  → 行程结束生成个人足迹
  → 可选补充感受和营养记录
  → 事实反馈用于更新路线
  → 下次旅行或周末探索再次使用
```

这个闭环里，“记录”服务于用户自己的旅程，也反过来提升下一位用户的攻略质量。

## 12. MVP 范围建议

### 第一阶段：证明路线有用

- 先做一个城市、20～30 条高质量人工路线。
- 支持按可用时间、起点区域和同行类型筛选。
- 路线详情展示顺序、时间、步行距离、点单建议、替代方案和更新时间。
- 支持收藏、开始路线、完成站点。
- 用现有到店记录补充事实，但不要求用户写长文。

### 第二阶段：证明用户愿意更新事实

- 到站快速反馈。
- 路线过期提醒和事实更新队列。
- 旅程结束自动生成个人回顾。
- 编辑审核后把用户更新合并进路线。

### 第三阶段：扩展内容供给

- 授权创作者合作。
- 城市编辑后台与版本管理。
- 主题征集和季节路线。
- 在平台正式能力允许时接入授权内容 API。

## 13. 关键指标

首阶段不要把首页停留时长当作核心成功指标。更重要的是：

| 阶段 | 核心指标 |
|---|---|
| 找路线 | 进入首页后 90 秒内打开路线详情的比例 |
| 做决定 | 路线收藏率、站点替换率、开始路线率 |
| 真正使用 | 开始后完成至少一站的比例、完整路线完成率 |
| 认真记录 | 到站事实反馈率、旅后补充率、有效更新采纳率 |
| 留存 | 收藏路线后的 7 日回访、完成旅程后的下一城市/下一路线使用率 |
| 内容质量 | 信息过期率、关店扑空率、路线中断率、用户纠错率 |

## 14. 当前需要确认的产品选择

后续视觉和功能设计前，建议依次确认：

1. 第一座重点城市是否仍为上海。
2. 首批路线更偏游客经典区域，还是本地社区街区。
3. 路线默认时长采用“2 小时 / 半天 / 一天”，还是以早餐、午后、夜宵场景组织。
4. 首阶段是否具备人工实地核验和持续更新内容的能力。
5. 是否愿意优先采用创作者授权合作，而不是自动抓取平台内容。

这五项决定内容成本、首页结构和后续数据库设计，应在下一轮 UI 设计前确定。
