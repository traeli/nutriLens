# 食迹簿记录模块产品需求

> 版本：0.3  
> 更新日期：2026-09-11  
> 范围：小程序“记录”Tab、到店体验辅助录入、私人营养识别

> 首页、城市路线、用户留存与外部内容来源的详细策略见 [`city-food-guide-product-strategy.md`](./city-food-guide-product-strategy.md)。在该策略完成确认前，不继续调整首页视觉实现。

## 1. 产品决策

“到店体验”和“餐食营养”是两个独立业务，不合并为同一种记录。

- **到店体验是主业务**：围绕具体地点，记录菜品、价格、排队、服务和用户本人结论，可以申请公开。
- **餐食营养是私人工具**：围绕一餐食物，估算热量和营养成分，默认仅本人可见，不生成餐厅评价。
- 两条流程可以复用识别结果，但不能共享发布状态、审核结论或内容可信度。

## 2. 记录首页

用户进入“记录”Tab 后先选择业务类型：

1. `记录到店体验`：主入口，视觉优先级最高。
2. `识别餐食营养`：辅助入口，明确标记为“私人小工具”。

页面必须解释：照片能够识别食物，但不能判断服务、排队和真实消费感受。

## 2.1 发现首页

首页定位为“城市隐秘饮食地图”，不承担全量餐厅搜索、实时附近推荐、餐厅评价表单或筛选器职责。

- 第一屏必须说明产品主题：走进街巷、市场和社区，寻找未被流量充分看见的本地日常饮食。
- 第一核心入口是可执行的街巷美食路线；征集活动属于第二屏以后的轻量运营入口。
- 主内容由实地核验的街区路线、具体小店线索、地方食物故事、最近核验记录和征集主题组成。
- `推荐 / 一般 / 谨慎选择`、价格、排队等字段属于单条到店记录的结构化信息，不作为首页常驻选项单独展示。
- 首页内容以文字编辑和信息层级为主，图片用于具体餐厅或记录的辅助识别，不能依赖单张大图完成视觉表达。
- 视觉统一采用“城市折页地图 + 随身食单”的生活化语言，以米纸底、墨色正文、深绿功能色和朱砂印记形成一个体系；活动不得随机增加独立主色。
- 中文标题和批注使用有手写感的楷体或同类字体，正文使用易读黑体；避免全页面使用端正、均匀、模板化的字形。
- 城市切换继续作为首页全局上下文，并同步影响记录页的默认城市。
- 不承诺“附近现在能吃什么”。营业和等待信息必须标注最后核验日期，并提示出发前再次确认。

## 3. 到店体验流程

### 3.1 基本流程

1. 选择地点；城市自动继承“发现”页的当前城市。未收录的新地点必须通过微信原生地图选点确认名称、地址和坐标，不允许只输入店名直接提交。
2. 填写或由助手整理到店日期、消费对象、人均消费、排队时间、菜品和体验描述。
3. 用户本人确认总体结论和体验标签。
4. 补充公开图片、私密消费凭证和可见范围。
5. 保存私人草稿，或直接提交后台审核；提交不要求手机号核验，审核通过后才会公开。

记录填写规则：体验标签和正文均为选填，正文没有最低字数要求，允许留空，仍保留 500 字上限。小程序只要求选择餐厅位置和本次感受，并自动填写到店日期。提交仍需登录、同意当前协议，并保留现有账号状态和提交频率限制。非空正文继续进行内容安全检测；空正文不调用文本检测，标记为不适用并进入人工审核。

### 3.2 AI 录入助手

助手的定位是“整理用户输入”，不是“替用户点评”。

允许的能力：

- 从用户文字或系统语音输入中提取价格、排队时间、菜品和标签建议。
- 从餐食图片中识别菜品名称。
- 从小票图片中提取消费金额、时间和店名候选。
- 提供总体结论建议，但必须由用户主动确认。

禁止的能力：

- 仅凭菜品图片生成餐厅好评或差评。
- 自动判断服务态度、排队体验、宣传不符等不可从图片证明的信息。
- 未经用户确认直接保存为事实或提交公开。
- 把营养评分转换为餐厅评分。

每个自动填写字段都应支持修改，并在首次整理后提示“已整理，请确认”。

### 3.3 语音输入

MVP 优先复用手机输入法的语音转文字能力，将最终文本交给同一套结构化提取流程，不额外采集或保存原始语音。

如果未来引入平台语音识别，必须单独说明录音用途、保存期限和第三方处理方。

## 4. 餐食营养流程

支持两种输入：

- 拍照识别食物及营养成分。
- 文字描述一餐，估算热量和主要营养素。

识别结果默认写入现有私人 `food_records`，不要求选择餐厅，不进入公开内容审核。

每次成功识别后应明确提示已保存，并在“我的 → 营养记录”展示：

- 累计识别餐次、食物数量和热量汇总。
- 最近识别的食物、用餐时段、日期和主要营养成分。
- 完整历史查看、按用餐时段筛选和单条删除能力。
- “仅自己可见，不参与餐厅评价”的数据边界提示。

完成后可以提供“加入到店记录”，但只复制菜品名称等客观字段到 `visit_record_versions.dishes`，不复制营养结论为餐厅结论，也不建立公开展示依赖。

## 5. 数据边界

| 业务 | 主数据 | 默认可见性 | 是否可以公开 |
|---|---|---|---|
| 到店体验 | `visit_records`、`visit_record_versions` | private | 审核通过后可以，提交不要求手机号核验 |
| 餐食营养 | `food_records` | private | 不通过餐厅体验接口公开 |

首版不新增两类记录之间的外键。用户选择“加入到店记录”时，仅复制一份可编辑的菜品草稿，避免删除营养记录影响公开体验历史。

## 6. 助手接口规划

P1 可新增统一的无副作用接口：

```text
POST /api/v1/record-assistant/extract
```

输入支持整理后的文字、菜品图片对象 Key、小票图片对象 Key；输出仅返回字段建议、来源和置信度，不直接创建 `visit_records`。

```json
{
  "suggestions": {
    "place_name": "梧桐面馆",
    "dishes": ["牛肉面", "卤蛋"],
    "average_cost": 34,
    "wait_minutes": 12,
    "tag_codes": ["taste", "service", "queue"],
    "conclusion": "recommend"
  },
  "sources": {
    "average_cost": "user_text",
    "dishes": "image_and_user_text"
  },
  "requires_confirmation": true
}
```

## 7. MVP 验收标准

- 进入记录页时能清楚区分两个业务入口。
- 营养入口不再嵌入餐厅评价表单。
- 到店体验中的图片入口文案明确为“识别菜品/小票”。
- 用户必须亲自确认总体结论和标签。
- 首页切换城市后，记录页自动使用同一城市。
- 图片、文字或助手失败时仍可完整手动录入。
- 营养识别结果不会直接生成或发布餐厅评价。
- 首页不再把结论、价格和排队字段当作独立频道或筛选项。
- 首页首屏能进入城市攻略和征集活动，并至少展示攻略、近期记录、征集三个内容层次。
- 每次成功营养识别后可从“我的”查看对应私人记录。


### 当前登录与记录提交行为

所有业务查询和写入均需要登录；会话保存到 Redis，默认两小时，小程序请求前临近过期自动刷新，双 Token 均过期后重新登录。创建新门店前必须取得当前选定城市编码；缓存尚未初始化时先加载城市，仍无可用城市则提示用户，不发送缺少 `city_code` 的请求。
